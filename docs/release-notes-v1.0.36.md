# Sakura Input 1.0.36

開発者向け入力履歴の保存・終了処理と、TSFからengineへの通信処理を修正しました。障害時に履歴を不用意に切り詰めたり、古い書き込み要求を採用したりする経路を防ぎ、キー処理中の通信に共通の待ち時間上限を設けています。

## 主な変更

- 履歴の復号・デコード失敗を明示的なエラーとして扱い、読めない履歴を破損末尾と誤認して切り詰めないようにしました。圧縮後の置換失敗も明示し、復旧が必要な状態で書き込みを続けません。
- 履歴のFlush／終了処理から不要な全件圧縮を外し、起動時の走査を一度にまとめました。定期処理は最も古い履歴の期限を使い、期限切れがない間の再書き込みを減らします。
- 履歴クリア前に作成を始めた記録の再流入、IDカウンターの周回、同じ保存先への重複所有を防ぎました。終了はworkerの実際の停止まで確認し、失敗を重複呼び出しにも返します。
- engineの起動時に通信口の所有権を先に確保し、重い初期化と利用可能な状態を区別しました。
- TSFの通常キー・テストキー・保存キーの各callback内で、IPC処理が50 msの共通期限を使うようにしました。途中まで届いた応答や取消競合では接続を再利用せず、古い要求を誤適用しないようにします。実際のWindows callback全体が必ず50 ms以内に完了する保証ではありません。
- TSFの書き込みjournalは、実際に要求された先頭ticketとcontext世代を照合します。
- Spaceキーの参照モデルとテスト用切断処理の不一致を修正しました。TLC検証スクリプトは実行失敗・時間切れ・古い証跡を成功扱いせず、検証対象と実行結果を記録します。

## 検証と残る課題

対象の回帰テスト、workspaceテスト、Clippy、依存関係監査、リリース用辞書の再現性・品質検査を実施します。検証用モデルの探索結果は、そのモデルと探索範囲についての結果です。

今回のリリースで全体再監査のすべての項目を完了したとはしていません。履歴の電源断・プロセスクラッシュ後の完全な復旧保証、実COMホストを使う全経路の受入試験、VS Codeクラッシュの原因特定、性能評価の残項目は継続調査です。AppContainerのCIで断続的に起きる実行ファイルパスの検証失敗（#104）には診断を追加しましたが、原因解決とはしていません。

## 更新方法

v1.0.33以降は設定画面の更新確認、または `sakura_settings.exe update apply` で更新できます。v1.0.32以前は、Sakura update-signing v2の公開鍵を持つ版へ一度だけ手動インストールしてください。

このReleaseはowner承認済みのAuthenticode未署名版です。Windowsには「不明な発行元」と表示されます。手動インストール時は、GitHub Releaseの `release-manifest-v2.txt` に記載したSHA-256と `sakura_setup.exe` の値を照合してください。

自動更新では、固定公開鍵によるSakura manifest署名、版・sequence・有効期限、installerのサイズとSHA-256を検証します。manifestが `authenticode=unsigned` を宣言し、`WinVerifyTrust` が正確に `TRUST_E_NOSIGNATURE` を返した場合だけ実行を許可します。不正署名・失効署名・未知provider・policy不一致は拒否します。

## 対応環境

Windows 11 build 22000以降、x64、AVX対応CPU。32 bitホスト用DLLとARM64ネイティブ版は含みません。
