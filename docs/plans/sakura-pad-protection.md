# Sakura Pad 全体・メモ単位の保護計画

状態: 2026-09-27 に承認、実装中。追跡先は
[#269](https://github.com/tsuyoshi-otake/sakura-input/issues/269)（既存 Pad は #92）。
最初の成果物は操作可能な画面試作と暗号処理の基礎。
画面試作は [`docs/prototypes/sakura-pad-protection.html`](../prototypes/sakura-pad-protection.html)。
実際の秘密を入力せず、画面内の固定デモ値だけで操作する。
既存のメモはユーザーが明示的に保護を有効にするまで従来の DPAPI 保存を使う。
開発中の Pad には全体・個別メモのパスワード保護経路が接続されたが、全計画の完了を意味しない。
実データの移行・リリース・インストール・外部サービス導入は行っていない。

進捗: 既存 Pad の最前面・タイトル保存修正は `6e23d78`。
rendererから独立した常駐暗号workerを呼び、明示的な全体保護設定で旧Padを
検証付きv3保存へ切り替える。再起動後のパスワード解除・暗号化保存・Windows
ロック時の表示マスクは、隔離したデータと実プロセスで確認した。設定画面に
Sakura Pad専用ページとPadを開く入口を追加した。個別メモは v4 と全体保護 v3 の
どちらでも独立したパスワードで保護でき、ロック時の一覧・検索・コピーは内容を伏せる。
新しい個別保護では復旧キーを一度表示し、Pad 外への保存確認後に保護を確定する。
解除・キャンセル・再表示は実 Windows UI と独立 worker で検証した。
全体保護でも復旧キーを一度表示し、保存確認前は旧データのまま、確認後は
パスワード・復旧キーの両方で解除できる。キャンセルと Windows ロック時の
キー消去・旧保存処理への復帰を、隔離した実 Windows UI で確認した。
YubiKey による鍵保護、TOTP の画面と永続状態、
自動ロック・保護設定変更・障害注入の総合検証は未完了。現状の検証と限界は
`verification/sakura-pad-protected-store.md` と
`verification/sakura-pad-memo-protection.md` に記録する。旧形式への後退防止の
初期検証は `verification/sakura-pad-protection-foundation.md` を参照。
ユーザーは YubiKey 5 シリーズを所有。FIDO 接続と Windows WebAuthn API v9
を読み取り確認したが、キーでの PRF 登録・解除成功を確認したものではない。

## 1. 提供する操作と保護範囲

| 対象 | 解除後に見えるもの | ロック中の動作 |
|---|---|---|
| Pad 全体 | 一般メモ一覧と、個別保護メモの閉じた項目 | 一覧・タイトル・本文・検索結果を表示しない |
| メモ単位 | 解除したメモのタイトルと本文 | 「保護されたメモ」とだけ表示。内容を検索・コピー・出力しない |
| 両方を設定 | Pad を開いた後、必要なメモだけ別途解除 | Pad の解除だけで個別保護メモを自動解除しない |

- 全体保護と個別保護は、それぞれ単独でも併用でも使える。
- 全体設定に「Pad を保護」「今すぐロック」、メモ操作に「このメモを保護」
  「このメモをロック」「このメモの保護を外す」を置く。保護設定の変更には再認証が必要。
- 初期案: アイドル 5 分、Windows ロック、スリープ、Pad を閉じる操作で
  全体をロックする。フォーカスを別アプリに移すだけではロックしない。
  個別メモは別メモへの切り替えでも再ロックする。タイムアウトは変更可能。
- 常に最前面でも、ロック後に古いタイトルや本文を一瞬表示しない。
  再起動・再表示・DPI 変更・テーマ変更・UI Automation でも同じ契約を守る。
- 個別メモの存在と件数は、全体保護が解除済みなら分かる。タイトルや日時で
  内容を推測できる表示は避ける。公開用の別名は初版では追加しない。

対象は、未解除のメモの閲覧と、保存ファイルを取り出して読む行為の防止。
解除中の Windows セッションを完全に支配するマルウェア、管理者による
プロセスメモリ取得、ユーザーが既に外へコピーした情報まで防ぐとは主張しない。

## 2. パスワード・YubiKey・TOTP の位置づけ

| 方式 | 設計案 | 実装の条件 |
|---|---|---|
| パスワード | パスフレーズから Argon2id で鍵を導出し、ランダムな暗号鍵を保護 | KDF の上限と端末での実測、認証付き暗号の検証を完了 |
| YubiKey | FIDO2 の PRF / hmac-secret による鍵導出を使い、暗号鍵の解除に結び付ける | Windows API・実機・ファームウェアで能力を確認 |
| パスワード + YubiKey | 両方の秘密がそろわないと鍵を解除できない方式 | 片方だけで開ける別の鍵包みを通常経路に残さない |
| TOTP | 任意の追加確認。暗号化の基礎には使わない | オフラインで提供できる保護の限界を明示 |

パスワードと YubiKey のどちらかで開ける「代替手段」と、両方必須の
「二要素」は別の設定として扱う。復旧手段を登録した場合は、それが別の
解除経路になることも設定画面で明示する。

通常の TOTP は共有秘密と時刻を使う。検証秘密と復号可能な鍵を同じ端末に
置いて UI でコードを照合するだけでは、アプリを迂回したファイル復号を
防げない。6 桁コードをそのまま暗号鍵にする設計も採用しない。
これは [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) の方式をローカル保管庫に
適用した場合の設計上の判断であり、TOTP 一般が無意味という意味ではない。

初版はサーバー不要のパスワード / YubiKey 保護を優先する。TOTP を付ける場合は
ローカル追加確認としての限界を明示する。TOTP の成功をファイル復号にも
必須にしたい場合は、別の信頼境界で鍵を解放するオンラインサービス等を
別計画にする。今回の計画だけで外部サービスの運用・送信を開始しない。

YubiKey は挿入検知やシリアル番号だけで認証しない。ランダムなチャレンジ、
本人操作、対応する PIN / user verification、用途ごとの鍵導出を使う。
登録途中のキャンセル、非対応キー、キー抜去、別キー、タイムアウトを区別する。
YubiKey の全機種で同じ方式が使えるとは仮定しない。
[Yubico PRF](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/)、
[Microsoft WebAuthn API](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/webauthn-apis)
に基づいて Windows 上の実機試作を先に行う。

## 3. 設定画面と UI/UX

2026-09-27 の追加要望: 暗号・認証だけでなく、設定場所、普段のメモ操作、
失敗・復旧までを設計対象に含める。この節は画面・操作の仕様案であり、
描画済みのモックアップや実機で検証済みの新 UI ではない。

### 3.1 設定への入口と情報の分け方

| 入口 | 開く場所 | 扱う設定 |
|---|---|---|
| Sakura Input の設定 → 入力・変換 → Sakura Pad | 専用の設定ページ | 起動ショートカット、全体保護、自動ロック、解除方法、復旧 |
| Pad のメニュー → Pad の設定 | 同じ設定ページへ直接移動 | 全体設定を探し直させず、二重の設定画面も作らない |
| メモの操作メニュー → このメモの保護 | 対象メモの保護設定 | 個別の解除方法、再ロック、復旧。全体設定へ誤適用しない |

現在、起動ショートカットは基本設定にある。専用ページへ整理する際は設定値・
既存 CLI を保持し、基本設定には移動先への入口を残す。同じ値を別々のフォームで
編集させない。保護対象のメモ一覧や件数は、Pad 全体のロック中に設定へ出さない。
既存の5つの大分類タブは維持し、「入力・変換」内の左ナビゲーションに項目を
追加する。Pad の設定だけのために大分類タブを増やさない。

設定ページは既存のネイティブフォームと同じ密度で、次の順に置く。
最初からパスワード・TOTP・YubiKey の入力欄を全部並べない。

```text
Sakura Pad

起動                     Ctrl を2回押す

Pad 全体の保護           設定済み · 現在は解除中
                         [今すぐロック]  [保護設定を変更…]

自動ロック               操作しない状態が [5分 ▾] 続いたら
                         Windows のロック・スリープ時は必ずロック
                         Pad を閉じたときもロック

解除方法                 パスワード
                         [YubiKey を追加…]  [追加認証を設定…]

復旧                     復旧手段を登録済み
                         [復旧方法を確認…]
```

未設定時は「この Pad は専用のロックを設定していません」と表示し、主操作を
「Pad 全体の保護を設定」にする。「安全」「暗号化済み」の一語だけで、Windows
ユーザー単位の保護と Pad 専用ロックを同じものに見せない。
設定済み / 未設定と、現在ロック中 / 解除中を別の状態として表示する。

普段の値変更と秘密を伴う操作では、保存の確定点を明確に分ける。
起動ショートカットなどの通常設定は既存の［適用］［OK］［キャンセル］に従う。
保護有効化・解除方法の変更・復旧キー更新は、専用の手順の最終ボタンで確定する。
この操作は後から親画面の［キャンセル］では戻らないことを、その最終画面で
短く示す。未適用の別設定を一緒に保存しない。自動ロック時間など保護ポリシーを
変える場合も、保護設定の一つの保存操作として再認証と公開をまとめる。

### 3.2 初回設定は3段階

1. **解除方法を決める** — 対象が「Pad 全体」か「このメモ」かを見出しに固定。
   最初の選択はパスワード。パスワードは貼り付け可能、確認欄と表示切替付き。
   意味のない強度点数は出さず、採用する長さ条件を入力前に示す。
   YubiKey 単独・併用は対応確認が済んだ構成で選べるようにする。
2. **復旧方法を用意する** — 復旧キーの保存または予備キー登録を行う。
   内容は画面を離れると再表示しない。保存後は画面をマスクし、保管した復旧キーの
   一部入力、または予備キーでの実際の解除確認を求める。チェックボックスだけで
   「復旧確認済み」にしない。復旧なしは詳細選択から明示的に選べる。
3. **内容を確認して有効にする** — 「対象」「必要な解除方法」「自動ロック」
   「復旧手段」を一画面で確認し、［保護を有効にする］で確定する。
   保存・検証完了後に初めて「保護を設定しました」と表示する。

戻る / キャンセルでは現在の有効設定を変えない。準備中の秘密・未完了登録は
終了時に解放する。公開の開始前まではキャンセル可能、原子的な切り替え中は
「設定を保存しています」と表示し、成功または失敗を確認してから閉じる。
見かけの進捗率は作らない。失敗時は「以前の設定を維持しています」など、
検証できた結果だけを示す。

### 3.3 日常の解除・ロックとメモ操作

- 全体ロック時は既存 Pad ウィンドウの中を解除画面へ置き換える。別の小窓を
  重ね続けない。見出しは「Sakura Pad はロックされています」、主操作は「解除」。
  本文やタイトルをぼかして背景に残さず、一覧を描画・UIA 公開しない。
- 個別ロック時は編集面に「このメモはロックされています」と「解除」を表示。
  通常メモの一覧はそのまま使える。解除失敗やキャンセルで別メモを操作不能にしない。
- 保護された行には鍵アイコンと「保護されたメモ 01」のような内容由来でない
  安定した番号を表示する。通常メモの「無題」と区別する。番号は暗号文の差し替え
  防止に使う ID とは別の表示上の識別で、件数・存在の公開範囲は節1の通り。
- 検索は解除済み内容だけを対象にし、検索中は「ロック中のメモの内容は検索しません」
  と表示する。照合したかどうか・ヒット件数・並べ替えから隠したタイトルを漏らさない。
  再ロック後は表示タイトル、プレビュー、検索結果、UIA の名前を同じ状態更新で消す。
- メモの操作に「今すぐロック」と「このメモの保護を外す」を別々に置く。
  前者は再確認なしで即時に隠す。後者は再認証と影響の確認を行い、通常の主ボタンと
  離して配置する。閉じたメモの削除も解除して対象を確認してから行う。

全体をロックしたら、個別解除セッションも失効する。解除後は直前の作業場所へ
戻すが、個別保護メモは閉じた状態で戻す。「前に開いていた」ことだけで再解除しない。
全体保護を設定していない場合も、Windows ロック・スリープ・Pad を閉じる操作で
解除中の個別メモを再ロックする。
狭い Pad では既存の 520 logical px の切り替えを使い、解除画面にも［一覧へ戻る］を
用意する。広い Pad では個別解除を編集面内で行い、他のメモを確認できるようにする。

YubiKey の OS 認証画面が Pad の最前面表示の後ろに隠れないよう、親 HWND と
フォーカス復帰を実機で確認する。常時の再前景化や点滅のループは作らない。
解除は明示操作で1回だけ開始し、挿入検知・再描画だけで認証を繰り返さない。

### 3.4 認証・失敗・復旧の表示

| 状態 | 表示と次の操作 | 終了後の状態 |
|---|---|---|
| 認証中 | 「確認しています…」、重複送信不可、［キャンセル］ | 成功時のみ対象を開く。取消なら閉じたまま |
| パスワード / コード不一致 | 該当入力の近くに理由と再入力操作。試行待ちなら残り秒数を表示 | 内容・タイトルを表示しない |
| YubiKey 未接続 / 非対応 / 抜去 | 「登録したキーを接続」「このキーは非対応」等を区別。再試行または登録済み復旧 | 無限待機せず期限で終了。未登録の代替手段へ自動変更しない |
| 保存失敗 | 「ロックしましたが、最後の変更は保存できていません」＋［再試行］。保存済みとは表示しない | 閉じたまま。詳細から復旧へ進める |
| 手段を紛失 | ［復旧キーを使う］［予備キーを使う］のうち登録済みの経路だけ表示 | 対象範囲だけ解除・再設定。復旧不能ならその事実とデータ保持を説明 |

TOTP は1つのラベル付き入力欄にし、6個の独立欄へ分割しない。貼り付けに対応し、
6桁がそろっただけで送信せず［確認］で送る。コード不一致、時計ずれの可能性、
試行待ちを区別する。QR の表示 → コードで確認 → 登録完了まで同じ対象を示す。
説明は「認証アプリのコードでも確認します」。ローカル確認の制約は設定時の
補足と説明リンクで示し、実現しない暗号化強度を表示しない。

復旧画面で入力するキーはパスワード同様にマスクし、ログや入力履歴に送らない。
「忘れた場合」を内容の消去や保護の無効化に直結させない。保護を弱める変更、
最後の復旧手段を外す操作では、対象と影響を明記してから確定する。

### 3.5 見た目・操作性・合格条件

Pad は `theme.rs` の既存の暖色系ニュートラルと桜色の選択レールを継承する。
Pad 本文16 / 補助13 logical px、8 logical px の基本余白、設定側は既存の
`presentation.rs` の文字役割・フォーム行を使う。秘密機能だけ別のダッシュボード風
デザインにしない。設定の配色は既存の `UiTheme` を使う。Pad と設定画面の
パレットが同じ実装だとは仮定せず、今回の計画にテーマの統合は含めない。
鍵マークだけに頼らず「ロック中」「解除中」「保護未設定」を
文字でも示し、OS のハイコントラストを優先する。

ボタン・入力・選択肢は通常、ホバー、押下、フォーカス、無効、処理中を定義する。
無効な理由は近くに表示する。主要操作は1画面に1つ。Tab 順序、Enter、Esc、
スクリーンリーダーの読み順・エラー通知を揃える。Esc で認証を取り消しても
編集内容の破棄や保護の無効化はしない。取消後は起点へフォーカスを戻す。
ロックによる内容の非表示は即時とし、フェード中に秘密を残さない。

| UI 検証項目 | Verify（実装時に追加する検証） | Expect |
|---|---|---|
| 設定の確定点 | `pad_protection_ui::settings_commit` で各段階の取消・失敗・親画面のキャンセルを操作 | 保存済み / 未保存が正しく表示され、別設定を巻き込まない |
| 二段階の対象 | `pad_protection_ui::unlock_scope` で全体解除 → 個別解除 → 全体再ロック | 個別ロックを飛び越えず、再表示・検索・UIA から旧タイトルも消える |
| 入力とフォーカス | `pad_protection_ui::keyboard_and_auth` をキーボード / UIA / 実 YubiKey で操作 | 全操作に到達でき、OS 認証画面が見え、二重送信しない |
| レイアウトと状態 | 幅519/520/521、96/144/192 DPI、light/dark/high contrast で全状態を描画・確認 | 長い日本語、エラー文、ボタンが重ならず、操作と保護状態が読める |
| 復旧と保存失敗 | `pad_protection_ui::recovery_and_save_failure` で紛失・失敗・取消を注入 | 次の操作が一つ以上示され、内容を漏らさず、消去へ誘導しない |

実装前に、設定ページ・全体解除・個別解除・復旧の4画面と主要な失敗状態を、
既存の見た目に合わせたクリック可能な試作で確認する。実際の秘密は使わない。
試作での操作確認と、本番の暗号・ネイティブ UI の検証は分けて報告する。

## 4. 現状と変更責任

現在の `pad_storage.rs` は `SKRLPAD2` v2 の文書全体を現在の Windows ユーザーの
DPAPI で暗号化する。最大 200 メモ、タイトル 256 UTF-16 単位、本文 65,536
UTF-16 単位、文書合計 4,000,000 UTF-16 単位。v1 からの読み込みにも対応する。
`PadWindow::new` は起動時に文書全体を復号し、`PadState` に保持する。
Pad 専用パスワード、ロック状態、TOTP、YubiKey の実装はない。

| 責任 | 所有する知識・状態 | 他の責任に渡す契約 |
|---|---|---|
| Pad UI | 表示中の解除状態、編集対象、マスク表示 | 世代付きの解除・編集・ロック要求と明示的結果 |
| 保護サービス | 暗号鍵、認証ポリシー、解除セッション、キャンセル | 許可されたメモのみの平文。失敗時は鍵・平文を返さない |
| 保存責任 | 新形式、暗号化エントリ、原子的公開、バックアップ、移行 | 検証済み世代、保存成功 / 失敗、復元結果 |
| 認証アダプター | パスワード KDF、Windows / YubiKey、任意 TOTP | 導出素材または認証結果。UI と保存形式を知らない |

暗号処理を各ボタンの実装へ分散しない。重い KDF を renderer の UI スレッドや
IME のキー入力経路で動かさない。鍵と認証処理は Pad 専用 worker を第一候補にし、
既存 worker の起動・接続元確認の契約と整合させる。新 crate / プロトコルの
必要性は試作で確定し、既存の AI ワーカーや IME 入力履歴に流用しない。
プロセス分離だけで同一ユーザーの悪意あるプロセスを防げるとはみなさない。

新しい公開契約は、要求 ID、解除世代、対象メモ ID、処理期限、最大長、
成功 / 拒否 / キャンセル / 期限切れ / 保存失敗を定義する。認証は同時に 1 件。
ロックや対象変更で古い結果を失効させ、遅れて返った成功で再表示しない。
自動再試行は行わず、必要な再試行は回数・間隔を制限する。

## 5. 暗号化・移行・復旧の設計

- 文書用と個別メモ用に独立したランダム鍵を使う。個別メモ用の鍵は、Pad 全体の
  鍵だけでは取り出せないようにする。全体ロック時は個別メモの鍵も解放する。
- AES-256-GCM 等の実績ある認証付き暗号を使う。形式版、メモ ID、鍵用途などを
  認証対象に含める。同一鍵の nonce 再利用、別メモへの暗号文差し替え、
  認証ポリシーの書き換えを検出する。既存ライブラリを使い、暗号を自作しない。
- パスワード原文や通常の DPAPI だけで開く代替鍵を保存しない。salt / KDF
  パラメーター / 暗号方式 / 鍵包みの版を明記し、不正な巨大パラメーターを拒否。
  鍵包みとデータ鍵を分離する方針は
  [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)
  に従う。Argon2id の値は端末の実測と既定の安全下限から決める。
- 新形式へ移行するときは v1 / v2 の原本を即上書きしない。新しい primary と
  backup を作成し、解除・内容一致を検証してから世代を切り替える。`.bak` / `.tmp`
  に旧方式で読めるメモを残したまま「保護済み」にしない。移行完了後に旧形式へ
  自動フォールバックせず、旧アプリは不明な版を拒否する。
- 現行 `PadStore::load` は primary の読取失敗時に backup / temp へ進む。
  新形式の暗号文を開けない場合や primary が消えた場合も旧 v2 を選ばないよう、
  切替完了を示す永続状態は復号後の文書ヘッダーから独立させる。保存責任が
  「未保護」「移行中」「保護済み」を判定し、保護済みでは v1 / v2 読取と書込を拒否する。
  現行 `ReplaceFileW` をそのまま切替に使うと旧 primary が `.bak` に残るため、
  移行専用の検証・公開・旧世代処理を別のトランザクションとして実装する。
- 移行途中の各書き込み・flush・置換・終了に障害を注入し、旧世代または検証済み
  新世代へ復帰できることを証明する。SSD・OS スナップショット・ユーザーの
  外部バックアップに残る過去データの安全消去は保証しない。
- 初回設定でランダムな復旧キーまたは予備 YubiKey を登録・確認する。
  復旧キーは Pad の外へ保存してもらい、原文を Pad に保管しない。
  個別メモにも独立した復旧設定が必要。全体の復旧だけで個別保護を解除しない。
  復旧経路を持たない選択も可能だが、失った鍵をリセットして内容を復活させる
  管理用の抜け道は作らない。
- パスワード変更、キー追加・削除、復旧は、旧手段の再認証、新手段での解除確認、
  原子的な鍵包みの更新、旧セッション失効の順。旧バックアップやコピーに対して
  過去の鍵を遡って無効化できるとは約束しない。

## 6. 実装順と完了条件

以下のテスト名は実装時に追加する予定の対象であり、現在の合格を意味しない。
Cargo テストは `ci/run-test-quiet.ps1` 経由、Windows の長い実行は TKW で記録し、
終了後は `ci/check-process-clean.ps1` で所有プロセスの終了を証明する。

1. **保護の基礎と全体ロック**
   - 節3の設定・解除・復旧の試作で操作を確認し、脅威モデル、状態遷移、
     鍵包み、保存形式、復旧の契約を固定する。
     YubiKey / Windows API の小さい実機試作で能力とキャンセルを確認する。
     パスワードでの全体ロックと安全な旧形式移行を実装する。
   - Verify: `pad_protection::crypto` / `pad_protection::migration` / `pad_protection::lifecycle`
     の既知ベクトル、プロパティテスト、故障注入テストを実行。
   - Expect: 誤パスワード・改ざん・中断で平文を返さない。失敗で原本を失わない。
     再起動は常にロック状態から始まる。KDF で IME 入力経路を停止しない。

2. **メモ単位の追加ロック**
   - 通常メモと個別保護メモの混在、個別の解除・再ロック・設定変更を実装する。
     鍵と平文の所有を対象メモ単位にし、ロックされたメモは復号せずに保持する。
   - Verify: `pad_protection::memo_isolation` と HWND / UIA 経由の `pad_protection_ui`。
   - Expect: 全体解除や別メモの解除で個別メモが開かない。ロックしたタイトルと
     本文が一覧、検索、プレビュー、ウィンドウ文字列、UIA、コピー、出力へ出ない。

3. **YubiKey による暗号鍵の保護**
   - 単独解除とパスワード併用を分け、実機能力に応じた対応範囲を公開する。
     予備キーと復旧キーを含めて登録・削除を実装する。
   - Verify: `pad_protection::hardware_key` のアダプター契約テストと実機テスト。
   - Expect: 別キー・PIN 拒否・抜去・キャンセル・非対応機種で未解除のまま終了。
     併用設定では片方だけで開けない。モック合格だけで実機対応完了としない。

4. **TOTP の任意追加確認**
   - ローカル確認の保護範囲を UI に明記し、必要なら全体 / 個別ポリシーに付ける。
     登録は表示した QR / 秘密のコード確認が済むまで未完了とする。
   - Verify: `pad_protection::totp` の RFC 6238 ベクトル、時計ずれ、再使用拒否、
     試行制限、時刻巻き戻し、登録中断、復旧テスト。
   - Expect: 許容窓外や同じ成功コードの再使用を拒否する。再起動やロールバックを
     含むローカル制限の限界を明記する。強いオンライン二要素保護は別途判断する。

5. **品質・漏えい経路・配布前の総合確認**
   - 認証中のロック、保存中の終了、ディスク不足、破損、遅延コールバック、
     スリープ、キー抜去を含む状態遷移を検証する。ロック直後に表示を隠し、
     未保存編集は暗号化済みスナップショットとして保存責任へ渡す。
     保存失敗時も再表示せず、未保存状態と再試行 / 復旧方法を知らせる。
   - Verify: 状態機械テスト、fuzz / fault injection、実 Windows UI テスト、
     wrapped workspace tests、fmt、clippy、現行 CI の依存ルール、cargo audit、
     worker リソース計測、プロセス終了チェック。
   - Expect: 全経路に観測可能な終端があり、遅い成功でロック解除が復活しない。
     ログ・履歴・AI 入力・エラーメッセージ・クラッシュ収集へ秘密を意図せず渡さない。
     保護前の Pad タイトル編集・自動保存・最前面・DPI・レイアウトに回帰がない。

解除した保護メモのコピーは明示操作だけにし、既定 15 秒で Pad がまだ所有する
現在のクリップボードだけを消去する。他アプリが後からコピーした内容は消さない。
OS の履歴・クラウドクリップボード抑止も検証するが、既に他アプリや外部へ渡った
コピーを回収できるとは表示しない。プロセス内の秘密は寿命を短くし、可能な
バッファを消去する。Win32 内部や OS が作るすべての複製の消去は保証しない。

依存パッケージは公開後 7 日以上の版だけを採用し、lockfile と audit を更新する。
実装は既存 checkout で行い、保護追加を理由に新しい worktree は作らない。
リリース・インストール・既存メモの実データ移行は、各検証を通した後の別の実行段階。

## 7. IRV と判断の境界

- A. 現状把握の範囲: `pad.rs` の生成・編集・コピー、`pad_storage.rs` の文書契約と
  DPAPI 境界、`pad_list.rs` の一覧契約、`pad_ui.rs`、README の Pad 節。
  AI 用 Credential Manager は転用可能性を確認しただけで、Pad の鍵保管として使わない。
  UI/UX の追加検討では設定のページ・ナビゲーション・保存契約と、Pad の
  `theme.rs`、設定の `presentation.rs` を参照した。
- B. 全体保護と個別保護には、起動時に全件復号する現在の構造と保存形式の変更が
  必要。そのため、タイトル修正より範囲が広い。暗号・復旧・漏えい経路は省略しない。
  設定 UI へ調査を広げた理由は、通常の［適用］と保護設定の確定を混同させず、
  現在の見た目・入力操作に沿って配置するため。
- C. まだ保護機能の責任移動や新しい依存はない。提案では、UI、保護サービス、
  保存責任、認証アダプターを明示契約で結び、鍵の所有を一か所にする。
- D. 次の作業は本計画から対象契約・検証へ進める。ただし未実装なので、IRV が
  実際に下がったとは主張しない。Windows API 能力、鍵包み、移行契約の追加理解が必要。
  UI の作業では節3から対象画面、文言、操作状態、予定テストへ進める。
