# Sakura Input 1.0.39

高負荷時に入力文字や変換状態が失われるという報告（#148）について、原因を特定するための観測手段を入れたリリースです。**症状そのものは、まだ直っていません。**

## 主な変更

- engineが1打あたりどこで時間を使ったかを段階別に記録し、`sakura_settings.exe diagnostics timing` で読み出せるようにしました。合わせて、通信のタイムアウトが実際に何ミリ秒待ったのかを記録します。
- 出荷ビルドに、engineを名指しの4地点（dispatch前、変換中、session更新後、応答送信前）で意図的に待たせる仕組みを入れました。これは負荷を再現するための試験用で、通常のインストールでは決して作動しません。詳細は下記。
- `sakura_settings.exe diagnostics faults` を追加しました。自分のengineでその遅延注入が1つも作動しない状態であることを、利用者自身が確認できます。
- engineとTSF DLLの間のプロトコルを21から22へ上げました。版が一致しないDLLとengineは従来どおり会話しません。

## 遅延注入について

試験用の遅延は、引数 `--fault-injection` を与えたときだけ作動します。この引数は、同時に `--test-pipe` が私設名前空間 `\\.\pipe\SakuraInputEngineTest-` のパイプを指しているときにしか受理されません。通常の名前でengineを起動する際にこの引数があると、engineは**起動を拒否します**。黙って動き出して入力を止めることはありません。環境変数やファイルからは有効化できず、起動後に有効化・再設定する経路もありません。

インストールされたengineでは全4地点が常に無効です。それは仮定ではなく確認できる主張で、`sakura_settings.exe diagnostics faults` が各地点の状態と発火回数を表示します。

## 検証と残る課題

format、Clippy、workspaceテスト（1,893件成功・91件除外）、Releaseビルド、installer生成を確認してリリースします。辞書の成果物は1.0.38と同一です。本リリースに辞書入力の変更はありません。

このリリースで実測により確定したのは次の2点だけです。engineを意図的に止めた状態でも、engine側で入力が欠落・重複・順序反転することはなく、古い応答が新しい要求の答えとして配送されることもありません。そしてクライアントが1打を待ちきれずに諦めた場合、そのキーはengineには適用済みであるのに、続く再同期でengineから捨てられ、再送もされません。つまりホストで文字が消えるとすれば、それはengineが失ったのではなく、その上の層が諦めた結果です。

**これは原因の確定ではありません。** 高負荷でその「諦め」がどれだけ起きるのかはETW実測前であり、想定している要因のいずれも原因と断定していません。実ホストでの再現確認も未実施です。#148で継続して追跡します。

VS Codeクラッシュの原因特定や解消を示すリリースでもありません。

## 導入方法

このReleaseはowner承認済みのAuthenticode未署名版です。Windowsには「不明な発行元」と表示されます。GitHub Releaseから取得した `sakura_setup.exe` のSHA-256を `release-manifest-v2.txt` と照合して、手動インストールしてください。Sakura固有のmanifest署名は、Windowsのコード署名とは異なります。未署名版は自動更新で取得・実行されません。

## 対応環境

Windows 11 build 22000以降、x64、AVX対応CPU。32 bitホスト用DLLとARM64ネイティブ版は含みません。
